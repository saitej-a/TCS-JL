## Planner resolutions

- **R1 — Assembly is a single-pass bounded subtree fetch (per CONTEXT's "Explicitly left to the planner").** `comment_page` is replaced by an assembly that fetches the page's top-level comments and then walks descendants to the render depth with a bounded number of queries (per-level batched `parent__in` queries or one recursive CTE — the executor picks against the measured budget; Django 5.2 on PostgreSQL, `idx_comment_parent_created` serves either). The budget test is rewritten with the new ceiling and the count comes from the same pass.
- **R2 — The render depth and breadth constants are named module constants** (working values 5 and 3, per the UI-SPEC's unresolved row), not magic numbers in a template.
- **R3 — The continue-this-thread fetch** is a query param on the existing thread route (`?parent=<comment_id>` returning that node's bounded subtree, same serializer) — no new route, one owner in `frontend/src/api/community.ts`.
- **R4 — Frontend tests extend the existing harness** (`CommentThread.test.tsx`'s adapter-swap + fixtures patterns); the depth-50 chain fixture is synthetic, built in the test, never committed seed data.
- **R5 — Serializer field names for counts/closed signal** are the executor's to finalize (`reply_count`/`descendant_count` in must_haves are indicative); the UI consumes whatever is shipped, pinned by tests both sides.
