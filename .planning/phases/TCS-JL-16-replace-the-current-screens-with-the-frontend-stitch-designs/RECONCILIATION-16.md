# Phase 16 — Reconciliation Record (literal Stitch markup)

One row per composition, and the rows are **read by a script**: `frontend/scripts/stitch-fidelity.mjs`
parses this table and checks, per screen, that the ported source still carries the composition's
class tokens, glyphs and headings, that every `data-awaiting` slot in the source is declared here
(and vice versa), and that none of the fabrication strings listed here appears in the source. A row
that lies fails the build; a column that gets renamed fails loudly instead of silently stopping the
check.

**Column meanings**

| Column | What it holds |
|---|---|
| Composition | the folder name under `frontend/stitch designs/` |
| Ported sources | the files rebuilt from it (paths relative to `frontend/`) |
| Awaiting slots | every `data-awaiting="…"` value in those sources — a slot whose concept the product does not have (D-02) |
| Not carried | class tokens (or literal copy) deliberately **not** ported, each with its reason in the prose section below. The check honours a declared drop for a class token, a glyph name and a heading alike |
| Fabrication kept out | strings from the mockup that must not appear in the source — the honesty check |
| Suite | the test file that pins the ported behaviour |
| Status | whether the row is actually verbatim today: `verbatim`, `verbatim*`, `chrome`, `variant` or `restyle` (not yet ported) |

> **Status (added by the Phase 16 audit, see `16-AUDIT.md`; kept current by the port itself).** The `Status`
> column records what is actually true of each row. The audit found that only one composition
> (`tcs_joining_tracker_login_screen_variant_a_split_trust_badge`) carried its markup, and that the 44 rows
> claiming otherwise were a Phase 12 restyle rather than the verbatim port this record claimed. Rows are now
> flipped forward as each screen is actually ported: as of the settings pass, **27 of 45 pass the
> mechanical check** (4 `verbatim`, 12 `verbatim*`, 3 `chrome`, 8 `variant`) and 18 are still `restyle` —
> every settings composition now passes. For a `restyle` row,
> treat `Not carried` and `Fabrication kept out` as incomplete — the divergence is real and was recorded in no
> column at all.
>
> `verbatim` = carries the composition with nothing dropped.
> `verbatim*` = passes the check because its gaps are declared dropped in this table (for the verify screens,
> the mockups' masked address and frozen countdown).
> `chrome` = a shell mockup; see below.
> `variant` = an **alternative composition for a screen another row already carries**. Several folders are two or
> more designs for the same screen (`personal_recruitment_timeline_1` vs `_2`, the dashboard's four designs, the
> desktop vs mobile community feeds, the two post-detail designs, the two milestone modals). A screen renders one
> design, so the chosen composition's row carries the markup and the rejected design's distinct tokens are declared
> dropped here — which is exactly the list this record previously omitted. The choice itself is stated in the prose
> section below.
> `restyle` = the screen renders the composition's layout with other classes; the row is not yet a port.
>
> `chrome` = a shell mockup: the composition's `<main>` is the center column, and it embeds a placeholder
> page body (a skeleton dashboard, or a demo "My Status Summary"). The row carries the chrome — banner,
> sidebar, top bar, tab bar — and declares the placeholder body dropped, because no real screen renders it;
> each page composition supplies the body instead. The dark-mode composition is `chrome` for a second
> reason: the app implements dark mode as `dark:` variants of the light markup, so it carries no second
> literal class set.

## Notes and Deviations
- **Strict Preserved Plumbing (D-02):** All API interceptors (`client.ts`), token refresh logic, route protection guards, Daphne ASGI WebSocket chat, and typing presence wave animations remain intact and unmodified.
- **Honest Awaiting State Contract (D-03):** Elements in mockups lacking backend data use `data-awaiting="<namespace>.<field>"` rendering `—`, strictly avoiding fabricated statistics.
- **Skin Scoping:** `.skin-v1` and `.skin-v2` scopes apply Tailwind theme customizations cleanly without component clashes.
- **Community variants.** `/community` renders **`community_discussions_feed`**. Its sibling designs
  (`community_discussions`, `community_discussions_empty_filtered_state`, `mobile_community_discussions_feed`,
  `mobile_community_feed`) are `variant` rows. The empty-filtered state is a *state* rather than a second
  screen, but the app renders it with its own `EmptyState` component, so that design is likewise not carried.
- **Shell compositions (`chrome`) — what is and is not the shell's.** `tcs_joining_tracker_app_shell` and `tcs_joining_tracker_desktop_app_shell_dark_mode` put the top bar *inside* `<main>`, and follow it with a skeleton placeholder dashboard ("Recent Joining Letter Dispatches (Live Stream)", "Regional Onboarding Waves & Batch Analytics"); `tcs_joining_tracker_mobile_app_shell` does the same with "My Status Summary" and "Community Pulse". The shell carries the chrome of all three verbatim — announcement banner, 240px sidebar, top bar, tab bar, the `expand_more` profile affordance and the sticky `top-9` offset — and drops the placeholder bodies: they are demo filler, and each page composition's own row supplies that page's real body.
- **Shell sticky offset (`top-9`) is conditional.** The compositions' `top-9` / `h-[calc(100vh-36px)]` offsets assume the 36px announcement banner is always rendered. The app's banner is data-driven and dismissible, so the chrome offsets only while it is actually on screen (`top-9` + `h-[calc(100vh-36px)]`) and otherwise sticks at `top-0` + `h-screen`. Both are in the source; the composition's assumption is the part that changed.
- **Shell notification dot (`top-1.5 right-1.5 h-2 w-2 ring-white`) — dropped.** The composition marks unread with a bare 8px dot. The app renders the real unread count in a badge (`notification-badge`), which is strictly more informative and is pinned by tests. The dot's tokens are the only chrome tokens the three shell rows drop.
- **Dashboard (`candidate_dashboard_1`) — every printed figure is fiction.** The composition prints `1,248 candidates`, `940 completed (75.3%)`, `210 candidates`, `Bangalore (42%)`, `64 days from survey`, the `22.3%` dispatch bar with its `Batch Dispatch Completion` label, `+18 this week`, `126 days since survey` with its `Above Avg` badge, `Verified Stage 4`, the three regional-telemetry rows (`84 JLs`, `52 JLs`, `In Verification`) and the external-channel cards (`4,280+ active members`, `r/developersIndia tracker`). None of these has an API basis, so the composition's rows, pills and bars carry the real payload fields instead, and the strings are listed in `Fabrication kept out`. The two rows with no field at all keep their composition markup and the `data-awaiting` contract.
- **Dashboard — the two `GET`-backed headings.** `HOW YOU COMPARE (2025 DIGITAL BATCH)` and `LATEST DISCUSSIONS IN YOUR STREAM (DIGITAL)` are dropped for the same reason the block-level D6 rule exists: no cohort batch is known, and the feed endpoint has no stream filter, so the second heading would claim a filter the API cannot apply. The blocks keep the composition's card, icon, rule and pill markup and state what they actually show. `LIVE REGIONAL ACTIVITY` and `CONNECT WITH PEER GROUPS` (and their `check_circle` / `send` / `open_in_new` / `forum` glyphs) are the two rail cards with no data source.
- **Dashboard — the three sample tints.** `bg-amber-50 border-amber-200` (status chip), `bg-amber-100 text-amber-800` (the `Above Avg` badge), `bg-sky-50 text-sky-700 border-sky-200` (the `JOINING_LETTER` category tag) and the `w-1.5 h-1.5` pulse dot are the composition's single sample state for elements the app renders from its tested badge matrices (`STATUS_BADGE_CLASSES`, `CATEGORY_BADGE_CLASSES`), which colour all 11 statuses and 12 categories. `w-[60%]` is the composition's hard-coded progress-line width; the port sizes that rule from the share of nodes actually completed.
- **Shell dark composition's literal classes — dropped.** `tcs_joining_tracker_desktop_app_shell_dark_mode` is a second full markup set in dark palette. The app implements dark mode once, as `dark:` variants of the light composition's classes (05 §4.2's class strategy), so tokens such as `bg-slate-900` and `border-slate-800` are carried as `dark:bg-slate-900` / `dark:border-slate-800`. The row declares the un-variant forms dropped rather than forking the shell into two markup sets.
- **Variant choices.** Where a screen has several Stitch designs, the port renders the desktop-first primary and the
  alternatives are `variant`:
  - `/timeline` renders **`personal_recruitment_timeline_1`** (the `max-w-7xl` two-column workspace with the vertical
    roadmap). `_2` is the 12-column design with the `pl-60` sidebar offset and its own rail cards; it is not rendered.
  - `/dashboard` renders **`candidate_dashboard_1`**. `_2` (the hero-and-benchmarks design) and the two mobile
    designs (`candidate_dashboard_mobile`, `mobile_dashboard`) are not rendered; the app uses one responsive page.
  Each such row's `Not carried` cell is the rejected design's whole distinct token set, so a future switch to that
  design is a visible diff in this table rather than a silent one.
- **Verify-email action (`Continue to your profile`) — dropped.** The composition's primary CTA links to `/onboarding/step-1`; the real flow routes through `/login`, because verifying an address does not authenticate a session. The verbatim markup kept the button, its `btn-brand-primary` treatment and arrow, and its secondary "Go to the dashboard instead" link; only the label and its target changed.
- **Verify-email action (`a***@example.com`) — kept out.** The mockup's "Candidate identity" row prints a masked address. This route has no session, so there is no address to show; the status panel states "Account status" alone rather than inventing an identity. The row's own `font-mono-code …` pill classes are still carried — they dress the attempted-token echo on the failure path.
- **Verify-email pending (`a***@example.com`) — kept out.** The composition prints the masked address inside the sentence; the port prints the real address the caller handed over in router state, and offers the editable field instead whenever no address is known. Masking an address the user must be able to correct would break the wrong-address path.
- **Settings compositions' inline `tailwind.config` tokens are real theme tokens (Phase 16).** Every settings
  mockup carries its own inline config, and four of the six declare named colours and radii there: the hub
  declares `brand` (`DEFAULT` `#0369A1`, `hover` `#075985`, `tint` `#E0F2FE`, `light` `#F0F9FF`), `slate`
  (`page`/`border`/`primary`/`secondary`/`muted`), `borderRadius.control` (`8px`) and `boxShadow.hover`. Rather
  than rewrite each class to the numeric scale holding the same byte (`#0369A1` *is* `--color-brand-700`,
  `#E2E8F0` *is* slate-200), `@theme` now declares them — exactly as `rounded-card`, `shadow-subtle` and
  `font-mono-numbers` were declared before — so the ported markup keeps the composition's own names. They are
  static light values paired with `dark:` variants, because the app implements dark mode once, as `dark:`
  variants of the light markup (05 §4.2), rather than as a second literal palette. This is a *presentation*
  deviation from Phase 12's vocabulary, not a behaviour change.
- **Settings hub — three declared drops.** (1) The composition's 40px `Save changes` button: the hub edits
  nothing — every card is a link to the page that owns that form — so a save button here would promise a write
  that cannot happen. Its tokens (`px-5`, `hover:bg-brand-hover`, `focus:outline-none`, `focus:ring-2`,
  `focus:ring-brand`, `focus:ring-offset-2`) are declared dropped with it. (2) The `Design note:` strip and the
  five per-card `Dark-theme note:` captions: they are the designer's annotations *to us* — dark-palette value
  reminders — not UI, and rendering "Card: #0F172A" to a candidate would be nonsense. Their tokens (`text-[11px]`,
  `bg-slate-100`, `border-slate-200`, `text-slate-400`, `px-1`) are declared dropped with them. (3) The
  composition's footer (`mt-12`, `pt-6`, `border-t`, `tracking-normal`): the shell composition owns the footer
  and `AppShell` already renders the real disclaimer, so a second one would duplicate it. The composition's
  `<main>` is likewise the scrolling column; the shell's own `<main>` fills that role, so `flex-1`, `px-8`,
  `py-7` and `overflow-y-auto` are declared dropped while the page's own `flex flex-col justify-between`
  `max-w-[1040px]` column is carried.
- **Profile form — the composition's two re-pointed cards, and its three dropped controls.** The port
  carries the breadcrumb, title block, both columns and the sticky bar, but three things the mockup draws
  have no API target: the avatar upload button (the avatar keeps its markup and shows the real initials —
  no serializer stores an image), the `Show my category badge on my posts` checkbox, and the recruitment
