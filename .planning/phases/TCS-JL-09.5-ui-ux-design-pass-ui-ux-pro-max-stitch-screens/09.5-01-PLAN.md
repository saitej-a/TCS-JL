## Task 2 — Settings hub (`/settings`) replaces its stub
**Files:** `frontend/src/pages/index.tsx` (remove `SettingsPage` stub), new `SettingsPage.tsx` + test, `routes/router.tsx` if imports need moving.
**Reference:** screen #1 `8926c8724c174a81817e8a8e4f5712aa`.

Account summary strip (name, **masked** email, verified chip, member-since in mono, status chip),
then the five section cards with real status values sourced from APIs where they already exist
(category/joining date from the profile API, push state from the PWA layer, device count from
`/devices/`). Cards must show an honest status line — never a hard-coded "3 devices".

**Accept:** every card deep-links to its route; each status line reflects real data or an explicit
"unknown" state; component test covers the loading and loaded states.

## Task 3 — `/settings/profile` (form + sticky action bar)

## Task 4 — `/settings/privacy`
**Reference:** screen #3 `d88ec4c0e3684fb3a9c4f9e157b5f614`.
Toggles for profile visibility / contact details / community, the search-engine-indexing notice
(default off), data export request, delete link, and the "What others see" live preview which
**must reflect actual current state**, not a static mock. The preview must be derived from the same
state the form edits (this is the cheapest place in the app to ship a lying UI).

**Accept:** toggling a control changes the preview within the same render; export request hits its
endpoint or is explicitly disabled with a reason; test pins toggle → preview propagation.

## Task 5 — `/settings/devices`**Reference:** screen #4 `f6707f3eff384d5c93bfbec1b10ebf59` (recovered via `list_screens` after its
generation call timed out — it had landed).
Push-state banner with the real `Notification.permission` value (the 9.4 work already distinguishes

## Task 6 — `/settings/security`
**No generated screen** — build from the #3/#4 row vocabulary: password change, 2FA state,
active sessions, sign-out-everywhere. If the layout outgrows those patterns, generate a screen
first rather than inventing chrome.

**Accept:** destructive/security actions require re-authentication or an explicit confirm step;
session revoke is reflected without a reload.

## Task 7 — `/settings/danger`
**Reference:** screen #5 `8f6ebe935fce467f9804244d4d04da9c`.
Export request + status, deactivate (reversible, clearly labelled), and permanent delete behind a
**typed `DELETE` confirmation plus an understanding checkbox**, with a 7-day grace-period note.
Deletion is the highest-consequence action in the product: the button must be disabled until both
conditions are met, and the copy must state exactly what is destroyed vs. anonymised.

**Accept:** the confirm cannot be satisfied by a single click; the endpoint contract (grace period,
what is anonymised) is verified against the backend before the copy is written; test covers
disabled→enabled transition and the abort path.

## Task 8 — Admin shell + `/admin/reports`
**Reference:** screen #6 `736288d341c24ac9bfd49aeaaa577bfd`.
Add the Administration nav group (Reports with live open-count, Announcements, Members) and the
moderator identity chip, **route-guarded to the moderator role** (the router must not merely hide
the link). Then the queue: status filter with counts, reason/sort filters, severity accent, bulk
select, export, and the row actions opening a moderation dialog.
**PII rule (hard):** reporter/subject identities render **masked only** (`a***@example.com`,
`+91 ******4321`). Reconcile every field name against the real 8.2 serializer — do not trust the mock.

**Accept:** the guard is tested for a non-moderator (must not render the data, not just the link);
the PII rule has a **test that fails if an unmasked email/phone reaches the DOM**; empty ("queue is
clear") state implemented.

## Task 9 — `/admin/announcements`
**Reference:** screen #7 `404937bf61c04f4f93885cd1aa7ace23`.
Composer (title, body with character counter, audience selector incl. by-category, send-now vs
schedule, push toggle, pin toggle, optional link) plus the published list with per-announcement
reach figures. The push toggle must reflect that delivery depends on each candidate's devices and
quiet hours — the same honesty rule as Task 5.

**Accept:** publishing hits the real broadcast path (preview + confirm before send); reach figures
come from the API; a scheduled post is distinguishable from a sent one.

## Task 10 — 404 route, error boundary, inline section retry
**Reference:** screen #8 `93aa0ebe4cac42c3bf43cd521ec84056`.
Unknown in-app routes → the 404 panel (with the requested path shown in mono); a render/API failure
→ the 500 panel with a **copyable reference id** and a collapsible technical detail; plus the inline
per-card retry pattern for a section that failed while the rest of the page loaded.

**Accept:** a genuinely bad URL renders the 404 panel with the app shell intact; a forced render
throw is caught by the boundary (test); the reference id shown to the user is the same one logged.
