## 1. Why this phase exists

9.2–9.4 built the SPA's real surfaces (auth, onboarding, dashboard, timeline, feed, post
detail, analytics, notifications, PWA). Three areas were left as **stubs or absent**, and the
repo's own verification records them as the remaining UI gap:

| Surface | State on disk before 9.5 |
|---|---|
| `/settings`, `/settings/profile`, `/settings/privacy`, `/settings/security`, `/settings/devices`, `/settings/danger` | one-line stubs in `frontend/src/pages/index.tsx` (`<StubPage title=… />`) |
| Admin console (`/admin/reports`, `/admin/announcements`, members) | does not exist in the frontend at all (the 8.2 backend APIs and admin triage workflow do exist) |
| 404 / render-error / empty-route states | no route or boundary surface exists |

So 9.5 = *design the undesigned surfaces, then implement them one by one* — with the design
work done through the `ui-ux-pro-max` skill and Google **Stitch** (MCP), so the reference
screens exist before code does.

## 2. Decisions taken before planning

**D1 — Scope is the undesigned surfaces**, not a redraw of the 32 screens 9.2–9.4 already
implemented. Those screens stay as shipped; 9.5 only adds what is missing.

**D2 — A new palette/type direction was authorised** (user decision). The skill recommends a
professional-blue + technical-type identity for this product category, and the app had been
running on the 05 §4 indigo/Inter layer. 9.5 therefore lands a **token v2** and reconciles
05 §4 with it (see §4).

**D3 — Stitch is the reference, not the deliverable.** Screens are generated under a phase-scoped
design system so the *next* surfaces (and future phases) inherit one coherent identity.

**D4 — Implement screen-by-screen**, in dependency order, each with its own acceptance check —
not one big-bang UI commit.

Output: `design-system/tcs-joining-tracker/MASTER.md`.

The skill classified the product as **Job Board/Recruitment** and selected *Flat Design* with a
professional-blue palette (`#0369A1` primary, `#0EA5E9` secondary, `#16A34A` accent) and a
**Fira Sans / Fira Code** pairing ("dashboard, data, analytics, precise"). That direction is a

because the app's busiest surfaces are data (timeline tables, analytics KPIs, a moderation
queue).

### 3.1 What was adopted vs. rejected (deliberate reconciliation)

The skill's output is a *recommendation layer*. Adopted/rejected explicitly, with reasons:

| Skill recommendation | Decision | Why |
|---|---|---|
| Primary `#0369A1`, secondary `#0EA5E9`, accent `#16A34A` | **Adopted** | This is exactly the Tailwind `sky` scale plus emerald-600, so it maps cleanly onto a token layer and keeps 4.5:1 on white. |
| Fira Sans for UI, Fira Code for data | **Adopted** (see §4.3 for the Fira Code boundary) | Technical mono for KPIs/IDs/timestamps is what the analytics and admin surfaces need. |
| Round 8px controls / 12px cards | **Adopted** — unchanged from 05 §4 | No reason to churn radii. |
| "Flat Design: **no shadows**" and `card { background: #F0F9FF }` | **Rejected** | A tinted page *and* tinted cards destroys the surface hierarchy the app relies on, and 05 §4 already mandates `shadow-sm` cards / `shadow-xl` modals. Keeping slate neutrals + subtle elevation. |
| Landing "Funnel (3-step conversion)" page pattern | **Rejected** | The landing page shipped in 9.2 and is spec-locked; this phase does not touch it. |
| Slate neutrals `#F8FAFC/#FFFFFF/#E2E8F0`, dark `#0F172A/#1E293B` | **Kept, not taken from the skill** | The skill pushed a `#F0F9FF` background. Slate is what every shipped screen, test and screenshot already uses, and it is what makes dark mode work. |

> **Open approval item (O-9.5-1):** the "Flat design / no shadows / tinted-card background"
> branch of the skill's output was **overridden**. If you want the literal skill palette
> (sky-50 page canvas, shadowless cards), say so before Task 1 — it changes the token file and

## 4. Token v2 — the 05 §4 reconciliation (proposed)

### 4.1 Where the tokens live (verified)

`frontend/src/index.css` holds the whole layer in a Tailwind v4 `@theme` block: the
`--color-brand-50…950` scale, `--font-sans`, and the §4.2 semantic aliases
(`--color-background`, `--color-surface`, `--color-primary`, …) whose dark values are
overridden under `.dark` in `@layer base`.

**Consequence: the palette/type refresh is a single-file change**, because components consume
`brand-*` and the semantic utilities rather than raw hex. Task 1 is therefore small; the real
work is the audit that no component hard-codes a hex.

### 4.2 Proposed brand scale (indigo → professional blue)

The skill's hexes *are* Tailwind `sky`, so the mapping is exact and reviewable:

| Token | v1 (indigo) | v2 (sky) |
|---|---|---|
| `brand-50` | `#eef2ff` | `#f0f9ff` |
| `brand-100` | `#e0e7ff` | `#e0f2fe` |
| `brand-200` | `#c7d2fe` | `#bae6fd` |
| `brand-300` | `#a5b4fc` | `#7dd3fc` |
| `brand-400` | `#818cf8` | `#38bdf8` |
| `brand-500` | `#6366f1` | `#0ea5e9` |
| `brand-600` | `#4f46e5` | `#0284c7` |
| `brand-700` | `#4338ca` | `#0369a1` |
| `brand-800` | `#3730a3` | `#075985` |
| `brand-900` | `#312e81` | `#0c4a6e` |
| `brand-950` | `#1e1b4b` | `#082f49` |

Two rules that differ from the skill's prose and matter for implementers:
- **Hover is *darker*, not brighter.** The skill lists `brand-600` as the hover of `#0369A1`;
  that is a lightening. Use hover = `brand-800`, pressed = `brand-900`.
- **In dark mode the accent is `brand-500` (`#0EA5E9`)**, because sky-700 `#0369A1` on a
  `#0F172A` surface does not reach 4.5:1. This is the one place the two themes intentionally
  diverge in *token choice*, and it must be stated per-surface.

`brand-200/300/950` are kept (they resolve §6.8's upvote-pill classes), which is why the scale
is swapped wholesale rather than trimmed.

### 4.3 Typography

- `--font-sans`: Inter → **Fira Sans**.
- `--font-mono`: currently a generic mono stack → **Fira Code** (with the existing stack as
  fallback), and it becomes the required face for *machine data only*: analytics KPI values,
  counts, table dates/times, device IDs, trace/reference IDs, OTP fields.
- **Boundary rule (must be enforced in review):** never body copy in Fira Code; never Fira Code
  below 12px. Tabular figures on so numeric columns align.

### 4.4 Spec reconciliation (the "deliberate" part)

05 §4 currently *is* the indigo/Inter contract, and 9.2–9.4 verification records cite it. 9.5
must therefore:

1. Amend `05_UI_UX_SPECIFICATION.md` §4.1/§4.3 to v2 **with the mapping table above**, and keep
   a short "superseded in 9.5" note pointing at this file rather than silently rewriting history.
2. Re-check the 32 shipped screens against v2 — expected to be a **token swap, not a redesign**,
   because they consume `brand-*`/semantic utilities. Any screen that fails that check is a real
   finding (hard-coded hex) and gets fixed.
3. Re-run the frontend gates after the swap (lint/typecheck/tests/build) — a re-skin that breaks
   a snapshot/aria query is exactly what the gate is for.

### 5.2 What the generated screens actually look like (verified, not assumed)

I opened screen #1's screenshot in the browser and inspected the render. It matches the brief —
240px sidebar with the active Settings item, account summary strip, section cards with real
status lines, rose Danger-zone card, footer disclaimer — **but it also contains annotation
artifacts that must not become UI:**

- visible caption lines reading *"DESIGN NOTE: …"*, including per-card dark-value mappings
  ("DARK THEME: token mapping…", "MARGIN BOUNDS WITH EXPLICIT DARK VALUE MAPPINGS THROUGHOUT"),
  because the prompt asked for dark-theme values to be annotated;
- an appended dark-mode sample strip below the page, plus a "Design System / Mode: Light" label.

**Treat these as margin notes on a mock, not as app chrome.** The prompts for #2–#8 asked for
the same annotations, so expect the same artifacts. Any implementation that renders a
"DESIGN NOTE" row is wrong. (This is worth doing once more per screen at implementation time —
reading the screenshot caught a real trap that reading the generation transcript did not.)

## 6. Risks / watch items

1. **Re-skin blast radius** — the swap touches every shipped screen. Mitigation: gate on
   lint/typecheck/tests/build, and treat contrast in *both* themes as part of the check.
2. **Admin surfaces are a new frontend capability, not a reskin.** The backend (8.2) has
   moderation triage and announcements with the ban protocol; the frontend has nothing, so
   Task 7 must reconcile against the real API contract rather than the mock's field names.
3. **Privacy constraints are load-bearing, not decorative.** The admin screens must never render
   an unmasked email/phone. The mocks demonstrate masked values; a naive implementation wired to
   a raw serializer would leak them.
4. **Stitch HTML extraction is still limited** (recorded in 9.3): the generated `htmlCode`
   download URL has not been readable in this environment. Screenshots *are* reachable — that is
   how §5.2 was done — so visual review is available even if markup extraction is not.
5. **`update_design_system` is unavailable in practice**, so no future session should assume the
   project default carries the v2 identity.
