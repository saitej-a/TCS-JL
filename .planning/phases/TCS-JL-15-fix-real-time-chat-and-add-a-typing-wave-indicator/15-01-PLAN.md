<objective>
Make real-time delivery actually work on the running stack and prove it with a real network client — no unit test is accepted as delivery evidence.

Purpose: The user's report ("The real time messages are not working") is reproduced at the infrastructure layer: `/ws/` is served by gunicorn (`config.wsgi:application`), a WSGI server that cannot complete a WebSocket upgrade, so every handshake is answered with Django's 404 and the browser falls back to REST behind an amber "Live updates paused" banner. Two further defects sit in the same path (nginx's missing read timeout on `/ws/`, and no origin validation on the router). Fixing them is a precondition for the typing feature in 15-02 — building presence on an unverified transport would repeat exactly what happened in Phase 13.

Output: an `asgi` (daphne) service beside the unchanged HTTP service, hardened `/ws/` proxy locations, an origin-validated router, a runnable backend test suite, and `scripts/ws_live_probe.py` producing recorded pass/fail evidence for handshake, delivery and idle survival.
</objective>

  <action>
  Create `scripts/ws_live_probe.py`: a standalone script run inside the `web` container (it has Django, channels, redis and the reachable compose network) that proves delivery over the real path — nginx → daphne → consumer → Redis channel layer → Postgres — and prints one `[probe] <check> PASS|FAIL <detail>` line per assertion with a non-zero exit if any check fails.

  Implementation requirements, all concrete:
  1. Bootstrap Django (`DJANGO_SETTINGS_MODULE` from the environment, falling back to `config.settings.local`), then ensure two deterministic local accounts exist and are usable for login (reuse existing rows when present; the login endpoint rejects unverified users, so set the verification flag the way `LoginView` requires).
  2. Over HTTP against nginx (`--base-http`, default `http://nginx`): `POST /api/v1/auth/login/` for both users to obtain bearer tokens, then `POST /api/v1/chat/ws-ticket/` with each token to mint one single-use ticket per user. Never log the tokens or tickets — print only their lengths.
  3. Open both sockets against `--base-ws` (default `ws://nginx`): `ws://<host>/ws/chat/<room>/?ticket=<ticket>` using the `websockets` library, and consume each socket's first frame, asserting `{"type": "chat.joined", "room": "<room>"}`.
     - check `handshake`: both connections completed and both `chat.joined` frames matched.
  4. check `delivery`: user A sends `{"action":"send","body":"probe <utc-iso> <uuid4>"}`; user B must receive a `chat.message` frame whose `message.body` equals the sent body within 5 seconds. Use a fresh unique body each run (the service layer's 10 s duplicate debounce would otherwise reject a repeated body, and a rejected send is not a delivery failure to be silently ignored — surface it).
  5. check `idle`: hold both sockets open, reading with a 75-second timeout, asserting neither closes and no error frame arrives (this is the F-2 regression guard; nginx's default read timeout is 60 s).
  6. check `auth`: a fresh third connection using an ALREADY-CONSUMED ticket must be refused (non-101 close), proving single-use auth survives the topology change.
  7. Add `--skip-idle` so the fast assertions can run per-commit without the 75 s wait; `--assert delivery,handshake,auth,idle` selects checks by name and defaults to all.
  8. Add a `--json` flag printing a compact machine-readable summary, and write the human-readable output to stdout only (no files).
  </action>
