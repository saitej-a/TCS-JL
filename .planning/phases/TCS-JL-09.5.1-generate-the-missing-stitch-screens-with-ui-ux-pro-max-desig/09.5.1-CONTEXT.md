## Implementation Decisions

### Copy truthfulness vs 05 §7.13

- **D-01:** The privacy policy documents only mechanisms that exist: email **masking**
  (`a***@example.com` on every public surface, including the auth screens), zero
  third-party trackers (verified: no analytics/ads dependency in
  `frontend/package.json`; `index.html` loads only the app bundle), per-device token
  scoping (9.4's `PushBackend.device_types`), and immediate delete-anonymisation.
  05 §7.13's "**email hashing**" order becomes a **named divergence** in the phase's
  VERIFICATION ledger — the same treatment 9.5 gave its 8 mock-vs-API divergences.
  The backend has no hashing (`grep hashlib|sha256|email_hash apps/accounts/` →
  nothing). — **Reversibility:** reversible — copy swap in a content module; the
  divergence ledger entry is the durable record either way.
- **D-02:** Account deletion is stated as **immediate, self-service, irreversible**:
  Settings → Danger Zone (`DELETE /account/` with the password) deletes on
  confirmation; email tombstoned, sessions/refresh tokens revoked, author rows
  anonymised. No grace period and no contact inbox. Screen #5's "executed within
  7 business days" and `hello@tjt-community.example` are recorded as fiction in the
  ledger (9.5 T7 verified the contract).
- **D-03:** Each page carries **one shared honesty sentence** rendered with the page
  (not buried in fine print) in the legal layout: the page describes how this
  community platform actually behaves and is not legal advice. Deliberately distinct
  from §5.6's three mandatory disclaimer placements, which are already shipped and
  pinned by `Disclaimer.test.tsx`.
- **D-04:** The no-trackers claim is **scoped to trackers/ads with the transport
  disclosed**: "no analytics SDKs, ad pixels or behavioural trackers", plus one clause
  naming the push path — browser push through the browser's own push service, native
  push via Firebase Cloud Messaging (`firebase-admin` is a real backend dependency),
  only for the notification types the user enables. Must NOT be readable as "no third
  parties anywhere".

### Frame: the §5.4 visitor shell

- **D-05:** Build the **§5.4 visitor shell** as a real shared layout for `/about`,
  `/privacy`, `/terms` (header nav `[LOGO] [Community] [About] … [Sign in] [Create
  account]`, footer link row above the disclaimer). Riding PublicShell/AppShell and
  staying chromeless were both rejected; screen #5's app-sidebar frame is the one part
  of its layout that contradicts §5.4 and is recorded as such.
- **D-06:** **Share the header/footer as components; Landing keeps its own page
  shell** (hero/sections/route) and composes them. Key scouting read: `LandingPage`'s
  header is only logo + `Sign in`/`Create account` (no `[Community] [About]`) and its
  footer is only `<Disclaimer variant="footer" />` — §5.4's chrome exists nowhere to
  "extract", so the shared components are new.
- **D-07:** The shared chrome is **auth-aware**: §5.4's nav for a visitor, account
  affordances once a session exists — mirroring how `AppShell` already degrades for a
  signed-out reader (PublicShell's comment: hides the email, routes account-needing
  links through `/login?next=<path>`). A logged-in reader arriving from AppShell's
  sidebar must not be shown `[Register]`.
- **D-08:** **Full §5.4 nav for both consumers, keeping the shipped button words:**
  the header gains `Community` + `About` (which §7.1's landing mockup at line 744
  already shows), the footer gains the `About • Privacy Policy • Terms of Service •
  Explore Community` row above the existing Disclaimer. Button words stay `Sign in` /
  `Create account` — shipped, friendlier than §5.4's `[Login] [Register]`, and pinned
  by `LandingPage.test.tsx:64–65`. Accepted consequence: landing visibly gains two nav
  links and a footer row. — **Reversibility:** reversible — component props and one
  page's JSX; the landing test pins give a fast feedback loop.

### Reconciliation depth for screens #1–#4

- **D-09:** **Correctness + the cheap controls.** Fix the password-policy mismatch
  via one shared rules source (D-10), state the real reset window
  (`PASSWORD_RESET_TIMEOUT = 3600` → 60 minutes — screen #4's "Token expires in 14m"
  was fiction), add token wrapping (`overflow-wrap: anywhere`), replace the resend
  `window.prompt` with an in-card flow (D-11), and add the skill-flagged show/hide
  toggles + submit-feedback triples. **Defer the 3-segment strength meter** — advisory
  scoring has no server equivalent, and a meter disagreeing with the validator is its
  own honesty problem.
- **D-10:** The password rules live in **one frontend module (`passwordRules.ts`)
  guarded by a backend test that reads it**: the module exports the five rules
  (min 10 + uppercase + lowercase + digit + special, matching
  `apps/accounts/validation.py`'s `ComplexityPasswordValidator` and 10_MVP_TASKS
  T2.4), and a Python test parses the file and asserts it against the validator —
  9.3 D7's one-module precedent with the repo's existing file-inspecting-test idiom
  (`test_phase_boundary.py`). The shipped bug is real on both password forms:
  `RegisterPage.tsx` and `ResetPasswordPage.tsx` gate and hint at "8 characters"
  while the server enforces 10 + four classes. — **Reversibility:** costly — the
  guard test couples two repos' files by path; moving either file means updating the
  test deliberately, which is exactly its job.
- **D-11:** The resend flow becomes an **in-card labeled email input**;
  `RegisterPage` navigates to `/verify-email-pending` with
  `{ state: { email } }` so the field arrives pre-filled (screen #2's design). Kills
  the `window.prompt()` at `VerifyEmailPendingPage.tsx:29` while keeping the API
  contract (`resend_verification(email)`).
- **D-12:** **No numeric expiry anywhere:** both verification pages keep
  "single-use and time-limited" qualitative copy. A hardcoded "24h" (T2.5's value)
  becomes the next "14m"-style bug when the server TTL changes; the 24h-vs-60min
  asymmetry belongs in the divergence ledger. A server-derived TTL endpoint was
  declined (same objection as the password-rules endpoint in D-10's alternatives).

### Legal-page shape and copy source

- **D-13:** Structure = **shared `LegalLayout` + three content modules** (data,
  not bespoke markup): one layout component owns the 65–75ch prose measure, the
  section TOC and the honesty line; each page is a content module exporting sections.
  Matches the codebase's existing pattern (`authCard.tsx` shared by the auth pages,
  `SettingsLayout` shared by six settings routes) and keeps copy testable as data.
  One routed tabbed page was rejected — it breaks §3.1's three distinct URLs that
  AppShell, RegisterPage and the new visitor footer link to.
- **D-14:** **Section TOC yes, `Last updated` line no.** A genuine in-page section
  TOC (anchor links per section — `/privacy` will have ~7) survives from screen #5;
  the version line does not: with no real publication history it is the same fiction
  as "TJT-Auth v2.4". Re-adding it later is one line in the layout once content
  actually changes.
- **D-15:** **Copy authorship is the user's**: you write the words for all three
  pages; the agent builds. Handoff (D-16) makes this non-blocking.
- **D-16:** **Handoff = build now, paste when ready:** the planner builds
  `LegalLayout` + content-module skeletons; the user pastes the final copy into the
  three content modules before execution finishes — the modules are data, so words
  swap in without touching markup. Nothing ships with placeholder prose visible.

### Claude's Discretion

- The specific React structure inside `LegalLayout` (how the TOC rail collapses on
  mobile, heading levels) — follow the app's existing responsive idioms.
- The exact section headings on each page, provided the user's pasted copy lands in
  the decided structure.
- Implementation details of the auth-aware chrome (AuthContext status wiring) —
  pattern already exists in `AppShell`.

## Existing Code Insights

### Reusable Assets

- `AuthCard`/`AuthField`/`ErrorStrip`/`SuccessStrip` (`frontend/src/pages/authCard.tsx`): the auth reconciliation lands inside these; toggles and wrapping extend, not replace.
- `Disclaimer` + the three pinned strings (`frontend/src/components/Disclaimer.tsx`): the model for the honesty line (D-03) — one component, one string, pinned by test.
- `Input`, `Button` (with `loading`), `ErrorBoundary`/`ErrorPanels`, `SectionRetry`: the form controls and feedback triples D-09 needs already exist.
- `SettingsLayout` (`frontend/src/layouts/SettingsLayout.tsx`): the existing shared-layout-with-rail precedent that `LegalLayout` mirrors.
- `AuthContext` (`frontend/src/context/AuthContext.tsx`): the session status D-07's auth-aware chrome reads.

### Established Patterns

- **Divergence ledger** (9.5 VERIFICATION §3): every mock/spec-vs-API gap is shipped honestly and recorded — this phase's §7.13 items (D-01/D-02) and screen #5's fiction follow it.
- **One-module vocabulary + guard test** (9.3 D7's categories; `test_phase_boundary.py`'s file-inspecting idiom): D-10's `passwordRules.ts` + backend test.
- **Layout routes compose chrome** (`PublicShell` wraps `AppShell`; `SettingsLayout` wraps settings children): the visitor shell follows the same shape.
- **44px minimum targets** and `min-h-[44px]` throughout the shipped chrome: the new header/footer must match (§5.4's nav, the footer link row).

### Integration Points

- `router.tsx` lines 61–63: the three routes gain `<VisitorShell>` (new layout route or wrapper element) while keeping their paths.
- `LandingPage.tsx`: header/footer JSX swaps to the shared components (D-06/D-08) — landing tests at lines 64–65 and the `disclaimer-footer` pin are the regression fence.
- `RegisterPage` → `VerifyEmailPendingPage`: navigation gains `{ state: { email } }` (D-11).
- `frontend/src/pages/index.tsx` barrel: the three `StubPage` exports become real page components; `StubPage` itself may lose its last consumers.

## Specific Ideas

- The user wants **§5.4's visitor shell built for real** — not a re-theme of what screen #5 rendered: screen #5's app-sidebar frame contradicts §5.4 and stays out of the product.
- **Landing stays visibly consistent with the spec**: it gains `Community` + `About` in the header and the four-link footer row, because §7.1's own mockup already showed them (D-08).
- **The copy is the user's authorship** (D-15) with a paste-when-ready handoff (D-16); the agent must not ship placeholder prose in its place.
- The honest-state pattern ("Not tracked yet / Not available yet" from screen #1 and 9.5 T6) is the tone for anything the pages can't claim yet.
