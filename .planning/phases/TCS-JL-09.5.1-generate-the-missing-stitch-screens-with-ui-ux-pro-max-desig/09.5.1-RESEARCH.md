## Findings

### F1 — The password show/hide toggles already ship (corrects UI-SPEC v1)

`frontend/src/components/Input.tsx` has a built-in reveal toggle for `type="password"`
inputs: it flips `type` password↔text, carries `aria-label="Toggle password visibility"`
and `aria-pressed={revealed}`, positions absolutely (`pr-10` on the control), and is
pinned by `Input.test.tsx:26` ("the reveal toggle flips the input type and keeps its
aria-label"). Both `RegisterPage` and `ResetPasswordPage` already render
`<Input type="password">`, so **both forms already show toggles**. The reconciliation
task for screens #3/#4 therefore *verifies* toggle presence (backstop assertion) rather
than building it. The genuine gaps on those forms are: the wrong password rules
(F2), no per-rule client feedback, and copy (F3).

### F2 — The password-policy mismatch is real, on both forms, and the fix point is one module

Server: `apps/accounts/validation.py` `ComplexityPasswordValidator` — min **10** chars +
upper + lower + digit + special, each failure a stable code (`password_too_short`,
`password_no_upper`, `password_no_lower`, …); wired via `AUTH_PASSWORD_VALIDATORS`
(`config/settings/base.py:196`) and `10_MVP_TASKS.md` T2.4.
Client: `RegisterPage.tsx` gates at `password.length < 8` (line 31), hints "Must be at
least 8 characters." (line 81), errors with the same number (lines 39/109);
`ResetPasswordPage.tsx` repeats it (`tooShort` line 22, hint, error string). A 9-char
password passes the client and 400s at the server with a message the form never
prepared the user for.
Fix shape per D-10: one `frontend/src/utils/passwordRules.ts` exporting the rules as
data (min length + the four required character classes with human labels + a
`validate(password)` helper returning failed rules), consumed by both forms; a new
backend test (`apps/accounts/tests/test_password_rules_parity.py`) parses that file and
asserts parity with `ComplexityPasswordValidator` — the repo's existing file-reading
idiom (`apps/notifications/tests/test_phase_boundary.py` uses `open(module.__file__)`
and `Path(__file__)…glob`), so the pattern is established. No new endpoint (the
`GET /auth/password-rules/` alternative was declined in discuss-phase).

## Validation Architecture

- **Unit-level (jsdom):** `passwordRules.ts` — a Vitest set-pinning test asserting the
  exported rule vocabulary (min length 10; upper/lower/digit/special labels) and
  `validate()` outcomes (9-char → fails min; "abcdefghi1!" → fails upper; valid →
  passes). Mirror of the 9.3 D7 category-module pin. Register/Reset form tests:
  submit blocked with per-rule errors; hint text states the real rules; toggle still
  flips type (existing Input pin covers the component; page tests assert the rules
  render from the module).
- **Unit-level (pytest):** `test_password_rules_parity.py` reads
  `frontend/src/utils/passwordRules.ts`, extracts the min length and required classes,
  and asserts equality with `ComplexityPasswordValidator`'s constants — the deliberate
  cross-stack guard (D-10). Fails loudly if either side drifts.
- **Behavioral (jsdom):** pending-page test — prompt() gone; email input prefilled
  from router state; resend calls the API with the field's value; cooldown +
  rate-limit strip intact. Visitor-shell test — visitor sees Sign in/Create account +
  nav links; authenticated status swaps the auth zone; footer link row + Disclaimer
  present; landing composes the same header/footer (regression fence =
  `LandingPage.test.tsx` pins).
- **Behavioral (static copy):** a Vitest content-module test asserting the banned-copy
  ledger never appears (e.g. "email hashing", "hello@tjt-community.example",
  "business days", "TJT-") and required facts do (masking shape `a***@`,
  "irreversible", FCM clause) — making D-01/D-02/D-04 executable rather than prose.
- **Live re-derivation (verification):** `npm run lint` / `typecheck` / `tsc -b` /
  `vitest run` / `build`; backend `python -m pytest -q` including the new parity test.
  Contrast spot-check of the new pages via the existing `contrast-audit.mjs` idiom.
